# VulnForge 提示词设计原则

> 本文档沉淀 flow 阶段提示词设计中反复强调的技巧，作为后续编写 task / skill / agent 提示词的统一准则。持续补充。
>
> 部分原则参考 Anthropic《Effective Context Engineering for AI Agents》。

## 0. 分层职责

提示词分四层，每一层只承载它该承载的东西，不越层、不重复：

| 层 | 承载 | 注入方式 | 特征 |
|---|---|---|---|
| **agent** | 安全专家的身份、思维方式、全局心智、跨环节通用的工作区与协作规则 | 系统提示词，常驻 | 讲专家怎么想、怎么自处；不讲单个节点的流程细节 |
| **skill** | 通用领域知识与方法论 | 动态激活 | 放到任意相关环境都可用；不含具体路径/产物名/flow 机制 |
| **task** | 当前阶段的目标、背景、产出什么、关键判据 | 首条 user message | 无关具体任务输入；不讲别的阶段做什么、不堆完整路径、不塞方法论 |
| **prompt** | 当前 run 的准确环境信息 | 拼在 task 之后 | 具体路径、本次 run 的输入输出位置、user_instruction |
| **schema + output-contract** | 输出结构校验 | 机械约束 | 不靠提示词自觉 |

判断一段文字该放哪层：换个项目还成立、且讲的是专家通用心智 → agent；换个项目还成立、是某类方法论 → skill；换个 run 还成立但绑定当前阶段职责 → task；只对本次 run 成立 → prompt。

### agent 是「专家」，不是「节点说明书」

agent 是常驻系统提示词，所有阶段都带着它。因此它只装**对每个阶段都成立的全局心智**：专家的身份与思路、认知螺旋的整体形状、人人都读的工作区核心、并发一致性规则。

- 用专家口吻讲身份与思路（「你先理解项目，再识别风险」），不写逐阶段职责清单（「decide 做…、onboard 做…」）。逐阶段清单会把「别的阶段做什么」塞进每个阶段的常驻上下文，诱导模型越权顺手把别人的活干了。
- 工作区只列**全局通用、人人要读**的结构（如 `knowledge/`）；某个阶段单独使用的中间产物路径不进 agent，下沉到对应 task。


### skill 编辑三删

skill 是纯领域知识，写/改时删掉三类内容：

1. **独立说教**——"很多误报源于…""这一步最关键"这类正当化散文。理由只保留 inline 一句。
2. **具体案例**——具体项目/漏洞的真实例子（某函数、某 CVE、某协议行为）。它们属于讨论/文档，不属于通用知识。
3. **flow 机制**——并发、统一维护、待办、产物路径、阶段间协作。这些是 flow/task 层的事。

## 1. 正向指引，而非禁令

用"应该做什么 / 可以查阅什么"来引导 agent，而不是用"不能做什么 / 禁止读某文件"来约束。

- ✅ 推荐：「decide 需要的全局信息在 wiki 与 coverage 中，据此做调度决策。」
- ❌ 避免：「decide 不允许读源码。」

原因：禁令会触发 agent 的规避/钻空子行为，且无法穷举所有禁止项；正向指引把注意力导向期望行为，覆盖面更自然。需要约束范围时，靠"规划好它该做什么"来收敛，而不是堆砌禁止清单。

## 2. 轻量化:核心任务简洁,上下文/输出清晰

阶段提示词第一版优先轻量。三段式:

- **核心任务**:一两句说清这个节点要做什么,简洁。方法细节下放到 skill,不在 task 里重复。
- **上下文(可用信息)**:清晰列出当前阶段能读什么、各是什么,让 agent 知道去哪取料。
- **输出**:清晰列出要产出什么、写到哪、用什么模板/schema。

不要在 task 里堆砌冗长的方法论或负面清单——方法论进 skill,约束靠正向指引 + output-contract。task 只承载"做什么 / 看哪里 / 产什么"。

## 3. 描述核心，不重复

描述核心比长篇大论重复说同一件事更有效。这是简洁准确性要求。

- 一个概念说一次，说准。不要在 task / skill / prompt 里反复重申。
- 同一件事在不同层只出现一次：方法论在 skill，环境描述在 task，具体路径在 prompt。
- 与原则 2（轻量化）互补：轻量化是少写，这条是不重复。

### 同一信息只设一个权威源

一条信息若在多层重复，模型会信「更近、更显眼」的那份；一旦两份不一致，近的会盖过远的。

- 工作区目录结构的权威源是 agent；task 不再重列产物完整路径，只说「产出什么」，落点引用 agent 或交给 output-contract。
- 曾经的教训：agent 已权威列出 `knowledge/wiki/...` 全路径，但 task 又写了裸相对路径，模型信了 task 里更近的裸路径，把产物写到了顶层错位置。

## 4. 说明目标，不讲反例

直接陈述要达到的目标与做法，不用「不是 A，而是 B」的对比句式，也不挂「否则会怎样」的说教尾巴。

- ✅ 「审计一个项目时，你先理解它，再识别真正的风险。」
- ❌ 「你的工作方式不是拿着已知漏洞清单逐条匹配，而是先理解一个项目……」
- ❌ 「以代码证据为准，不靠猜测下结论。」→ 「以代码证据为准。」

反例与套话占字数、稀释重点，且把模型的注意力引向「不该做的事」。例外：当需要给判断**定阈值**时（如「证据不足时宁可标记不确定，也不夸大」），二选一的表述是在指方向，可保留。

## 5. 找到正确的海拔

提示词既不能像 if-else 硬编码那样脆弱，也不能泛到假设模型自己懂上下文。正确的海拔是：**具体到能引导行为，灵活到能留给模型判断空间。**

- 太低：把执行步骤写成流水线（「先读 X，再写 Y，然后检查 Z」），模型机械执行，遇到边界情况不会调整。
- 太高：只写「做好安全审计」，模型缺乏具体信号，输出不可控。
- 正确：task 约束输入和输出（「产出什么、满足什么条件」），不约束执行过程。

task 模板四段式就是这个海拔的落地：

```markdown
# 目标      → 做什么、不做什么
# 相关信息  → 去哪里取料
# 产出      → 产出什么、满足什么条件
# 备注      → 不归入产出但必须注意的约束
```

## 6. 最小高信号

context 是有限资源，token 越多，模型注意力越分散（context rot）。每一条信息都要问：**这条 token 能不能去掉？去掉后行为会不会变差？** 只有去掉会让行为变差的才是高信号。

- 长会话 task（如 poc-verify，动辄 50-120 turns）的提示词要最短——模型精力应留给执行，不是留给理解提示词。
- 先写最简提示词，跑一轮看失败模式，再针对性补——不要预防性堆规则。
- 能用一句话说清的，不用三句；能用示例说清的，不用规则列表。

## 7. 示例优于规则

模型从示例学到的模式比从规则列表学到的更可靠。与其写五条字段说明，不如给一行 canonical example：

```markdown
| R12 | 派发 hunt | ADV-R1-C2-A1 | 已有高价值 ADV，优先推进到风险假设 | 若形成 HYP，下一轮 verify |
```

示例的选择标准：**多样、典型、能体现预期行为**。不要堆砌边界用例，几个 canonical example 胜过一长串规则。

## 8. 文件系统是信号

模型可以通过文件名、目录结构、frontmatter status 快速获取状态概览，不需要逐个读文件。在相关信息段提示用 `grep`/`ls` 快速获取状态：

```bash
# 比 read 100 个 finding 快得多的状态概览
grep -R -l 'poc_status: pending' findings/BUG-*/report.yaml | wc -l
```

VulnForge 的编号系统本身就是强 metadata：

```text
BUG-R1-C2-A3-H1
    ↑  ↑  ↑  ↑
    第1轮 第2个COG 第3个ADV 第1个HYP
```

从文件名就能读出完整 lineage，不需要打开文件。

## 9. 工具职责不重叠

如果人类工程师说不清某个场景该用哪个工具，模型也说不清。每个工具应该职责单一、无歧义：

| 工具 | 职责 | 不应做的事 |
|---|---|---|
| `read` | 读文件内容 | — |
| `coverage` | 查看代码阅读覆盖 | 不应变成读文件内容 |
| `workspace_diff` | 查看自上次基线以来的文件变化 | 不应变成读文件内容 |
| `output-contract` | 校验写权限和 schema | 不应指导「怎么写」|

`workspace_diff` 看「变了什么」，`read` 看「内容是什么」——边界要清楚。

## 10. 先简后补

提示词第一版优先轻量。跑一轮，看到失败模式，再针对性补。不要一次性堆满预防性规则。

这条和原则 6（最小高信号）互补：最小高信号是静态目标，先简后补是动态过程。
