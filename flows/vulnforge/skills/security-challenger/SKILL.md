# security-challenger

安全假设证否技能。从防御者视角审查已证实的漏洞假设，尝试推翻它。

证否的目标不是"找代码里有没有防护"，而是**质疑这个漏洞在真实系统的真实威胁模型下，攻击者是否真能造成实质破坏**。代码路径可达只是必要条件，不是充分条件。很多漏洞在代码层面成立，但在实战中无法利用或价值有限——证否的职责就是把这些情况找出来。

## 归属判断（先问，决定性）

在查防护之前，先问两个归属问题——它们决定这个 bug 到底算不算被审组件的漏洞。

1. **攻击者前提是否合法**：假设依赖的攻击者，在系统的信任模型里是不是已经受信的角色？受信角色"滥用"自己被授予的能力不算漏洞。
2. **责任边界是否落在被审组件内**：触发危害的**最后一步**，是否由被审组件无条件执行？若最后一步依赖下游消费方（脚本、插件、调用方）的特定行为才发生，根因在下游而非被审组件。**下游是否"普遍这么用"不作为裁决依据**——普遍的误用仍是误用。

任一归属问题答"不合法/在下游" → 假设不成立，无需再查防护。

## 证否的两个层面

归属成立后，证否分两个层面进行，缺一不可：

### 层面一：代码防护

针对已构建的攻击路径逐一检查：

1. source 到 sink 之间是否存在边界检查、类型校验、白名单、sanitization 使路径不可达或输入不可控？
2. 触发路径是否需要特权配置、罕见编译选项、非默认构建依赖、或多步用户交互？
3. 即使到达 sink，实际影响是否被运行时机制降级？
4. 该代码模式在上游是否属于已知的、有意的设计选择（documented behavior）？

每一项检查必须给出**具体代码位置或明确的"未找到"**，不得笼统带过。

这一层回答的是"路径在代码上是否成立"。但代码成立 ≠ 实战可利用——这是层面二要解决的问题。

### 层面二：威胁模型对抗评审

代码路径成立后，跳出代码，站在**维护者/防御者的对抗立场**重新审视：即使路径可达，攻击者在真实系统的真实威胁模型下，是否真能造成实质破坏？

维护者收到漏洞报告时，通常会从以下几个维度反驳。证否要主动替维护者把这些反驳找出来：

**1. 攻击前提的独立性**

攻击路径通常依赖若干前提（攻击者位置、已有权限、信道控制等）。逐个追问：这个前提若成立，是否说明系统在更根本的层面已经失守，以至于本漏洞没有独立的安全增量？

- 若前提本身意味着"系统已经全面被攻破"，则本漏洞无独立价值——攻击者不需要它也能达成同样的破坏。
- 典型迹象：攻击前提要求攻击者已控制某个受信入口或已获得某项权限，而该入口/权限的失守本身已是更严重的问题。

**2. 威胁模型中的其它信任边界**

攻击路径往往只画出了 source→sink，但真实系统里可能存在**路径外的信任边界**已经把攻击者挡住。这些边界不写在漏洞路径的代码里，却决定攻击者能否真正触达。

- 系统在攻击者到达 source 之前，是否要求其通过独立的认证、凭据校验或其它身份/位置验证？
- 这些边界是否构成了攻击者无法绕过的独立前提（而非路径内可被绕过的检查）？
- 区分两类防护：路径内的检查（可被本漏洞绕过，不算有效对抗）vs 路径外的独立信任边界（攻击者必须先满足，才算有效对抗）。

**3. 攻击时序与窗口**

即使路径可达、边界可过，攻击者能否在**可操作的时间窗口内**完成触发？

- 触发是否依赖某个瞬态状态（初始化窗口、竞态窗口、某个中间状态的存活期）？
- 攻击者能否稳定地命中这个窗口，还是需要极端的时机巧合？
- 时序约束是否使攻击在实践中不可行或极低成功率？

**4. 真实增量价值**

即使漏洞客观存在且可触发，修复它能否真正提升安全性？还是被其它独立缺陷完全稀释？

- 若系统存在更根本的同类缺陷（例如本路径的防护失效，但同类的其它路径也都不防护），修复本漏洞不改变整体安全姿态。
- 若危害的最终达成还依赖另一个未确认/未修复的独立缺陷，本漏洞单独不构成完整威胁。
- 增量价值越低，越倾向于不成立或降级。

**5. 上游状态**

该缺陷在上游是否已被替代、修复或标记为已知设计？

- 是否存在更新的实现/组件已正确处理（即使旧组件未修）？
- 是否属于已文档化的设计权衡而非缺陷？
- 是否在受影响版本之外已修复？

每一项若有发现，必须给出**具体证据**（代码位置、commit、文档链接、版本对比），不得笼统带过。

## 裁决

核心问题：**攻击者拿到这个漏洞后，能否在真实系统的真实威胁模型下造成实质破坏？**

假设成立需要同时满足：
- 代码路径成立（层面一未找到有效防护）
- 实战可利用（层面二未找到有效对抗）：攻击前提独立、路径外无信任边界拦截、时序可行、增量价值显著

若代码层面成立但威胁模型层面存在重大对抗因素（前提不独立、被路径外边界拦截、时序不可行、增量被稀释），假设不成立——在论证中写清"缺陷在代码层面成立，但在真实威胁模型下不可利用/价值有限"。若缺陷本身值得继续追（例如待其它缺陷修复后再评估），按所在流程的回流机制记录，不要直接丢弃。

### CVSS 与裁决的一致性

CVSS 向量必须如实反映攻击前提（AV/PR/UI）和攻击复杂度（AC）。若威胁模型对抗评审发现攻击存在额外前提或更高的触发难度，AC 应相应提高；若攻击前提不独立，应质疑整个向量的成立性，而非单纯调高 AC。

不得出现“裁决写不成立/降级，但 CVSS 仍标低复杂度/高分”这种自相矛盾。
