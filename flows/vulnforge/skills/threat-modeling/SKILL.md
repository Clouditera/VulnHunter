# threat-modeling

威胁建模技能。为一个目标系统建立威胁模型——审计全程的判断基准。

## 核心心智模型

威胁模型先于找漏洞，回答“谁会攻击、攻击什么、哪里是边界”。后续每个漏洞判断都回到它检验——一个“技术上为真”的问题，若攻击者前提不合法或根因在信任边界外，就不是这个系统的漏洞。

## 一个威胁模型要回答

- **攻击者是谁**：匿名网络访客 / 已认证低权用户 / 恶意对端 / 本地用户等，**各自的初始权限**。
- **攻击者想要什么**：RCE / 提权 / 数据窃取 / 拒绝服务等。
- **攻击者不能做什么**：明确列出攻击者不能控制哪些输入、不拥有哪些权限、不在哪些位置。这能防止严重性虚高：一个“技术上为真”的 bug，若攻击者实际上控制不了触发输入，就不是高危漏洞。
- **信任边界画在哪**：哪些输入来自边界外（不可信），哪些组件/角色是受信的。
- **受信前提**：协议/架构设计上本就受信的角色，明确写出来。这一条最常被忽略，却是拦住“受信角色滥用=漏洞”这类误报的关键。

## Evidence Anchor

威胁模型里的每个架构声明必须有代码位置支撑，不允许空口主张。

- “这个角色是受信的” → 引用代码里哪里体现了这个信任假设（如某处跳过了校验、某处直接使用未消毒输入）。
- “信任边界在 X 和 Y 之间” → 引用边界两侧的代码（如解析入口函数 + 内部处理函数）。
- “攻击者不能控制 X” → 引用代码里哪里限制了 X（如硬编码配置、非外部暴露的 API）。

这些事实根据让后续分歧可以被快速核实；没有代码位置支撑的声明不适合作为威胁模型判断基准。

## 演进

威胁模型是活文档，随认知深入演进——出现新攻击者、信任边界要重画、某受信前提其实站不住时，都应更新。但攻击面细分、子路径枚举属于模块认知，不写进威胁模型。
